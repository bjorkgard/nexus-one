## Step 0 record

### 0A. Premise

Real problem: every later step's "Test" line (2.x to 7.x) reads scene state through `window.__nexus` and Playwright (`docs/PLAN.md:19`). Without the harness, each step would invent its own probe or rely on pixels. Do-nothing cost: 1.8 (`rendererInfo()` e2e), 1.9 (CI Playwright smoke) and every Phase 2+ e2e are blocked.

The plan solves the pain directly for test runners and the camera/renderer half of the API. For `getAgent`, `emit`, `setClock` it solves a proxy: their backing systems do not exist, so 1.3 can only ship names, not behavior.

Question: D1 — R1: Should 1.3 ship all six debug functions, or only the three that have something real behind them?
Project/branch/task: nexus-one, `feat/3-test-harness-debug-api`, task 1.3.
ELI10: The plan says the test hook `window.__nexus` should have six functions. Three of them (camera, screen projection, renderer stats) can work today. The other three (find an agent, inject an event, set the clock) need the event schema, the mock clock and the agent store, which arrive in steps 1.4, 1.5 and 4.5. We can fake them now, or let each later step add its own function when the thing behind it exists.
Stakes if we pick wrong: a test in Phase 2+ calls `__nexus.emit` or `setClock` expecting real behavior and gets a stub, or the later steps forget to wire them and the debug API stays half-built.
Recommendation: B because each function then lands with the code and the test that make it real, and the registry keeps `__nexus` open for later steps without editing one central file.
Note: options differ in kind, not coverage — no completeness score.
Pros / cons:
Header: Debug API
A) All six now, three as stubs
Build the fixed object from PLAN.md; `getAgent`, `emit`, `setClock` throw "not available until task 1.4/1.5/4.5". Effort S (human ~3h / CC ~15min), risk low. ✅ Type shows the full intended API today. ✅ No stubs that throw. ❌ Optional members push `?.` checks into every e2e and hide a missing hook until runtime.
Net: B trades a small plan edit for an API with no fake parts; A keeps the plan text but ships three stubs.

## Section 4 — Data Flow & Interaction Edge Cases

```
 e2e spec ─► nexus(page, "project", [x,y,z]) ─► waitForFunction(window.__nexus?.project)
             │ nil: hook absent      → TimeoutError "hook project not registered within 10s"
             │ wrong type / NaN      → TypeError from project() (D15), surfaced as evaluate rejection
             │ behind camera         → { x, y, visible:false } (D15)
             ▼
          page.evaluate ─► registry ─► Bridge closure ─► useThree() camera/gl/size ─► plain JSON back
             │ stale (HMR remount)   → old entry unregistered by cleanup (D14)
             │ duplicate             → Error "already registered" → pageerror → E2 fails
```

Async ordering. Invariant: an e2e call reaches a live hook bound to the current camera.

- Order 1: helper polls before Bridge mounts → member undefined → poll continues → resolves after register. Safe by `waitForFunction`.
- Order 2: StrictMode register → unregister → register. All three run in one synchronous commit; `waitForFunction` polls on animation frames, so no poll can land between them. Mechanism: React runs the double effect synchronously in the same commit.
- Order 3: HMR swap during a test: cleanup unregisters, new mount registers; a call in between fails loudly (undefined member) rather than reading a dead camera. Accepted: tests do not edit sources mid-run.
  Regression proof: registry unit tests cover register → unregister → re-register and duplicate throw (D14).

Interaction edge cases: no user-facing interaction is added (dev-only API). Double-call of hooks: idempotent reads. **OK**.
