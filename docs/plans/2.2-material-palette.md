## Landscape check

Search ran via WebSearch (Aside not installed).

- [Layer 1] Share one material and one geometry across meshes; instance or merge for draw calls ([R3F scaling performance](https://r3f.docs.pmnd.rs/advanced/scaling-performance), [codrops instances](https://tympanus.net/codrops/2025/07/10/three-js-instances-rendering-multiple-objects-simultaneously/)).
- [Layer 2] Sharing a geometry does not batch draws; separate meshes still cost one call each ([dev.to R3F gallery](https://dev.to/alanwest/why-your-react-three-fiber-gallery-drops-to-5-fps-and-how-to-fix-it-4661)). Cached geometry needs a shared lifetime; do not dispose it from one user while others remain ([r3f-geometry skill](https://claude-plugins.dev/skills/@EnzeD/r3f-skills/r3f-geometry)). Count materials by traversing into a Set; `info.programs` differs from material count in both directions ([three.js forum](https://discourse.threejs.org/t/does-three-js-optimize-and-not-swap-programs-for-materials-of-the-same-type/6012)).
- [Layer 3] The 30-material cap is a proxy. The real costs are shader programs (compile hitches) and draw calls. A palette with few materials and per-instance colour (vertex or instance colour) gets both cheaply, and it is also what makes the look coherent: one set of surfaces, many tints.

## Step 0 record

### 0A. Premise

Real problem: Phase 2 builds about eight kinds of geometry in seven steps. Without one palette, each step picks its own colours and materials, the look drifts, and material and program counts grow with every step. Target outcome: every later step pulls surfaces from one palette and shapes from one cache, the campus reads as one designed object, and the budget holds by construction. Do-nothing cost: colours scatter across 2.3-2.8 (CLAUDE.md "Coherent style" names 2.2 as the point where reuse starts), and 2.10 discovers the material and program counts too late. The plan step addresses the pain directly; its Done-when (material count in a scene that does not exist yet) is a proxy that needs a by-construction check.

Question: D2 — R5: How long should cached geometry live?
Header: Cache life
A) App-lifetime cache (recommended)
Geometry built once per key and kept until the app closes; a dev warning fires if distinct keys pass a threshold (default 256). Effort S, risk low. ✅ Nothing can dispose a shape another mesh still uses, including under StrictMode and HMR. ✅ Smallest API: get(kind, params). ❌ A key explosion (for example per-agent sizes) grows memory until the warning catches it.
B) Reference-counted cache
acquire/release pairs; the last release disposes. Effort M, risk medium. ✅ Memory returns when a floor or vehicle type leaves the scene. ✅ Scales to dynamic content. ❌ Every user needs paired effects; a missed release leaks, an extra one frees a live shape.
C) Plain memo map, callers dispose
Cache only dedups; disposal stays with callers. Effort S, risk high. ✅ Smallest code. ✅ Familiar useMemo pattern. ❌ One unmount disposes geometry still drawn elsewhere, giving blank meshes.

Answer: "App-lifetime cache (recommended)". Applied: the cache never disposes; `getGeometry(kind, params, build)`; key = kind plus params with sorted keys and numbers rounded to 1e-4; dev `console.warn` once when distinct keys pass 256. Amended by spec review: a dev-only `clearGeometryCache()` runs on HMR dispose so token edits rebuild shapes; it disposes nothing (live meshes are about to remount) and resets size, hits and misses to 0. Tests: same instance per key, different instance per differing param, key order and float noise map to one key, warning fires at the threshold.

Question: D3 — R6: How do we stop one object from recolouring every surface that shares its material?
Header: Mutation
A) Rule plus dev freeze (recommended)
Write the rule, add a counted variant() helper, and in dev freeze each palette material's Color objects so a stray color.set throws at the line that did it. Effort S, risk low. ✅ Bugs surface at the culprit line, not as a mystery recolour later. ✅ Deliberate variants stay visible in the budget. ❌ Scalar props (opacity, roughness) are not frozen; the rule covers them.
B) Rule only
Document the rule and the variant() helper, no runtime check. Effort S, risk medium. ✅ Zero dev-only code. ✅ Same API as A. ❌ A stray mutation in 4.11 glow work recolours every monitor silently.
C) Clone per object
Each mesh gets its own material copy. Effort S, risk high. ✅ Mutation is always local. ✅ No rule to remember. ❌ Breaks the 30-material cap with the first floor of desks.

Answer: "Rule plus dev freeze (recommended)". Applied: `palette.ts` header and README state that palette materials are read-only and per-object tint goes through vertex or instance colour; `variant(name, overrides)` returns a cached clone that counts against `MATERIAL_BUDGET`; in dev, `Object.freeze` on each palette material's `color` and, when present, `emissive` (`MeshBasicMaterial` has none) so a stray `.set` throws (ES modules are strict). Tests: frozen colour throws in dev mode; `variant` returns the same instance for the same overrides and counts in the budget.

### Rules

- Palette materials are read-only. Cached geometry is never edited after build (D12). Per-object colour goes through `InstancedMesh.setColorAt` only; vertex colours are allowed only when baked in by the builder with the colour data in the cache key (the slab pattern). A deliberate different material goes through `variant(name, overrides)`, which caches by canonical override key and counts against `MATERIAL_BUDGET`. Budget count = palette size + variants + `KNOWN_EXTERNAL.length` (today `["drei Grid"]`); invariant `count < 30`. Variant clones are frozen in dev like palette materials. Freeze runs after construction (`setValues` writes colours in the constructor).
- Glow hierarchy (Q5): trimCyan edges > LEDs > idle screens > lit surfaces; trimWhite stays below trimCyan. `LOOK.emissiveCeiling = 1.5`: no palette or variant `emissiveIntensity` above it (unit test). The board's screen swatch shows two instances, idle and active, so the gap 4.11 animates across is visible.
- Lit trims glow per material, not per object; per-object glow uses `screen` or `led`.
- `variant(name, overrides)` accepts only `{ color?: <TOKENS hex string>, opacity?, roughness?, metalness?, emissiveIntensity? }` (D13); unknown keys, non-hex colours and non-finite numbers throw; keys that cannot take effect on that material throw (eng X4: opacity only on transparent glass, roughness/metalness only on Standard, emissiveIntensity only where emissive is set); key = name + overrides through the cache canonicaliser.
- `variant` throws on an unknown palette name or when it would reach the budget; the error names the budget and current count.
- Geometry cache never disposes. Key: `kind` + JSON of params with sorted keys, numbers rounded to 4 decimals, `-0` normalised to `0`. Non-finite numbers throw (error names kind and param). Builders must be pure; the first build for a key wins.
- **Swatch board layout (E1):** two rows centred on the origin, on the slab top. Row z = -6: one 4×4×4 box per palette material except `ground` (the slab already shows it, and `swatch-box` has no colour attribute, so a `vertexColors` box would render black): 9 swatches; `furniture`, `screen` and `led` swatches are single-instance `InstancedMesh`es with their default instance colour (`TOKENS.surface.furniture`, `.screen`, and `TOKENS.surface.trimCyan` for `led`); glass is a 4×4×0.2 `swatch-pane` placed at the glass slot with an extra `panel` backer box (same `swatch-box` geometry, not the panel swatch) offset -2 units on x and -2 on z (away from the camera, which sits in the +x, +y, +z octant per `src/world/camera.ts:7-11`) so the pane sits between camera and backer. Outside-voice correction O2. Row z = +6: one `InstancedMesh` of 8 boxes on `paint`, colour per instance via `setColorAt` from `TOKENS.paint`. Pitch 6 units. Trim and LED swatches (Q4): `trimCyan` and `trimWhite` each show a `panel` cube framed by 12 edge bars (0.08 × 0.08 × 4.08 m, cached key `swatch-edge`, rotated per edge) on the trim material, matching mockup B; `led` shows 6 dots (0.25 m cubes, key `swatch-dot`) on a `panel` backer. All swatch shapes come from the geometry cache (keys `swatch-box`, `swatch-pane`, `swatch-edge`, `swatch-dot`), so `cacheStats().size` is 5 with the board open.
