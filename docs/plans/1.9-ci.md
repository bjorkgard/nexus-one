Question: D1 — D1: Which runners should CI use?
Project/branch/task: nexus-one, feat/9-ci, task 1.9 CI plus #106 packaged boot.
ELI10: CI needs a machine to run our checks. Our e2e tests draw 3D with WebGL, and the packaged-app test only runs on an Apple Silicon Mac. Linux machines are the usual cheap default, but recent Chrome on Linux runners has no WebGL unless we turn on a deprecated software renderer. Our repo is public, so Mac runners cost nothing extra here.
Stakes if we pick wrong: Linux e2e could fail on WebGL (red for a reason unrelated to the code), or pass on a software renderer that hides Mac-only rendering bugs; later perf (2.10) and visual (10.5) checks inherit the choice.
Recommendation: A because the product only ships on macOS arm64 (D3), the packaged test needs that runner anyway, and one job avoids a WebGL workaround in test config.
Note: options differ in kind, not coverage — no completeness score.
Pros / cons:
A) One macOS arm64 job (recommended)
✅ Tests run on the only platform we ship (D3), so a green run means the shipped target works
✅ One job, one cache set, no Chromium WebGL flag added to the Playwright config
❌ macOS runners queue longer and run slower than Linux; whole pipeline is one serial job
B) Linux job for gates + e2e, separate macOS job for pack
✅ Fast Linux feedback for lint, types and unit tests; macOS work runs in parallel
✅ Matches the common open-source CI layout most contributors expect
❌ Needs `--enable-unsafe-swiftshader` in playwright.config.ts and two cache setups
C) Linux gates job, then macOS job for e2e + pack
✅ Fast Linux feedback on cheap checks; WebGL e2e still runs on the shipping platform
✅ macOS job only starts when cheap checks pass, saving macOS time on broken pushes
❌ Two jobs and two installs; e2e waits for Linux job, so total time to green grows
Net: A trades some speed for one faithful job; B and C buy fast Linux feedback at the cost of a WebGL workaround or a second install.
Header: Runners
A) One macOS arm64 job (recommended)
One `macos-15` (arm64) job runs install, check, test, build, dev-server e2e, pack and the packaged boot test in sequence. Effort S (human ~2 h / CC ~15 min), risk medium (P4 unverified until first push), reuses all existing scripts. ✅ Runs on the only shipped platform (D3), so green means the shipped target works. ✅ One job and one cache set; no WebGL flag added to Playwright config. ❌ macOS runners queue longer and run slower; the pipeline is one serial job.
B) Linux job + macOS pack job
`ubuntu-latest` runs install, check, test, build and dev-server e2e with SwiftShader enabled; a parallel `macos-15` job runs pack and the packaged boot test. Effort S (human ~3 h / CC ~20 min), risk medium (P3, deprecated software WebGL). ✅ Fast Linux feedback for lint, types and unit tests; macOS work runs in parallel. ✅ Matches the common open-source layout most contributors expect. ❌ Adds `--enable-unsafe-swiftshader` to playwright.config.ts and two cache setups.
C) Linux gates, then macOS e2e + pack
`ubuntu-latest` runs install, check, test and build; a dependent `macos-15` job runs dev-server e2e, pack and the packaged boot test. Effort S (human ~3 h / CC ~20 min), risk medium (P4). ✅ Fast Linux feedback on cheap checks; WebGL e2e still runs on the shipping platform. ✅ macOS job starts only after cheap checks pass. ❌ Two jobs and two installs; time to green grows because e2e waits on the Linux job.

**Workflow `ci.yml`** (D1, S0, E1, E2, R1, R2/D10, D12, C1-C17):

- Triggers (R2 via D10, C14), literal block: `on: { push: { branches: [main] }, pull_request: {} }`. All PRs, whatever their base; no job `if:`. Each PR commit runs once; branches without a PR get no CI.
- `permissions: contents: read`. `concurrency: { group: ci-${{ github.ref == 'refs/heads/main' && github.run_id || github.ref }}, cancel-in-progress: true }` (E2, C16): each main run gets its own group, so no main run is cancelled, pending or running; PR runs share `ci-refs/pull/N/merge` and supersede each other.
- One job, id `ci`, on `macos-15` (arm64; D1), `timeout-minutes: 30` (C2).
- Steps, each failing the job on non-zero exit (no `continue-on-error`, no `|| true`): 0. Every `uses:` pinned to a full commit SHA with a `# vX.Y.Z` comment (S3-1/D12).
  1. `actions/checkout`
  2. `actions/cache` for `~/Library/Caches/electron` and `~/Library/Caches/ms-playwright`, key `electron-pw-${{ runner.os }}-${{ hashFiles('package-lock.json') }}`, `restore-keys: electron-pw-${{ runner.os }}-` (C1, C13, C17)
  3. `voidzero-dev/setup-vp` with `node-version: '26'` (C4), `cache: true`, `run-install` as a YAML block scalar string `|` containing `args: ['--frozen-lockfile']` (step inputs are strings; setup-vp README:220-222) (C1, eng E-1/D1, outside OV-1): the one install fails if `package-lock.json` is out of date
  4. `vp exec playwright install chromium`
  5. `vp check` (type errors fail here first)
  6. `vp test`
  7. `vp exec playwright test` (dev-server e2e: smoke, source, perf) (C5)
  8. `vp run pack` (runs `vp run build`, so build and its bundle guards are covered; R1). The pack script ends `electron-builder --dir --publish never` (eng E-2/D2), so CI never publishes implicitly.

## Section 4 — Data flow and interaction edge cases

```
  INPUT (commit, lockfile) -> VALIDATION (check/test/e2e/pack/boot) -> TRANSFORM (dist/, release/)
        -> PERSIST (caches on success; artifacts on failure|cancel) -> OUTPUT (check run "ci")
  shadow: lockfile changed -> key miss -> restore-keys prefix (C17) -> partial hit -> install fills gap
  shadow: cache corrupt/partial -> install or electron-builder re-downloads; worst case red at pack -> re-run
  shadow: two PR pushes -> E2 cancels older (cancelled, artifacts C9); main runs never share a group (C16)
  shadow: stale cache after Electron bump -> key changes with lockfile -> new download
```

Async ordering: the only shared state is the cache store and the `ci` check on a SHA. Invariant: the required `ci` on a PR head SHA reflects a real run of that SHA. Mechanism: one trigger per SHA (D10: PR SHAs get only `pull_request` runs; main SHAs only `push` runs), no skipped runs. Cache writes: `actions/cache` keys are immutable once saved, so two runs racing to save the same key leave one entry; the loser logs a warning, not a failure.
