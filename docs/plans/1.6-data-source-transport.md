Question: D1 — D1: How should the client avoid double-applying events across reconnects? Project: nexus-one, task 1.6 (#6, sub-issue #91). ELI10: when the app reconnects, the server sends a fresh picture of the world and then new events. If an event is already in that picture and is also sent again, token totals count it twice. TODO #91 says "remember recent event ids and skip repeats". That misses one case: an event folded into the new snapshot that the client never saw as a delta has no id in the client's set, so it can still be applied twice. A sequence number on every server message closes that hole. Stakes: wrong token and cost totals with no error (D10 of task 1.4). Recommendation: C, because it keeps the TODO's id set (which also guards `__nexus.emit` and mock duplicates) and adds the snapshot cursor that closes the overlap case, for a few extra lines in `protocol.ts`. Completeness: A 5/10, B 8/10, C 10/10. Net: C costs about one field per message and one comparison.
Header: Dedup
A) Bounded recent-id set only
Do what TODO #91 says: keep the last N applied ids and drop repeats. Effort S, risk medium, reuses nothing new. ✅ Smallest change; matches the TODO word for word. ✅ Also guards duplicates from MockSource and `__nexus.emit`. ❌ An event already inside a fresh snapshot but never seen as a delta still double-counts.
B) Snapshot cursor only (epoch + seq)
Every server message carries the server's `epoch` and a `seq`; the snapshot says which `seq` it includes, and the client drops older deltas; a new epoch (collector restart) resets. Effort S, risk low. ✅ Closes the snapshot-overlap hole exactly, with constant memory. ✅ Handles collector restarts in 9.4 by epoch. ❌ Drops the TODO's id set, so in-process duplicates (mock, `__nexus.emit`, a producer bug) go through.
C) Cursor plus bounded id set (recommended)
Both: epoch + seq for the server stream, and the bounded id set in the shared client apply step for every source. Effort S, risk low. ✅ Covers the snapshot overlap, collector restarts and in-process duplicates. ✅ Satisfies TODO #91 as written and adds one test for the overlap case. ❌ Two mechanisms to explain and test instead of one.

### Data flow: live path (four paths)

```
  HAPPY: ws open -> hello{v,epoch} -> snapshot{seq=N, state} -> onSnapshot(state)
         -> event{seq=N+1, event} -> parseEvent ok -> apply(cursor, ids) -> reduce -> onEvent(event)
  NIL:   message with no type / null body -> parseServerMessage fails -> drop + count + status stays
  EMPTY: snapshot with empty state (no sessions) -> onSnapshot(empty) ; zero-length frame -> parse fail path
  ERROR: socket error/close -> status=reconnecting -> backoff -> new socket -> hello(epoch') ->
         epoch' != epoch ? reset cursor : keep -> snapshot replaces state -> deltas with seq <= cursor dropped
```

### Data flow: mock path

```
  HAPPY: createMockStream(seed) -> clock tick -> events with ts <= now -> apply -> reduce -> onEvent
  NIL:   no events due on tick -> nothing emitted
  EMPTY: stream exhausted -> status stays 'open', no more events
  ERROR: setClock(ms) backwards -> rebuild state by replaying from start to ms -> onSnapshot(state)
         (a seek cannot un-apply events; replay is the only correct path, per 1.5 D13)
```

### LiveSource state machine

```
   idle --subscribe--> connecting --open+hello--> open --close/error--> reconnecting --timer--> connecting
     ^                     |                        |                       |
     +----unsubscribe------+-----unsubscribe--------+------unsubscribe------+--> closed (terminal)
  Invalid: open without hello (first message not hello -> close socket, reconnecting);
           event before snapshot in an epoch (drop + count); any transition out of closed (guarded).
```

### Scaling

10x / 100x: the mock at 100 agents (perf budget, `docs/PLAN.md:23`) and 4.5's 10,000 events/min (`docs/PLAN.md:290`). First to break: the snapshot, if ended sessions and agents are never pruned (it grows for the whole run), and a full `checkStream`-style id set if unbounded. Bound N is in Section 4; retention in Section 7.

### Single points of failure

One WebSocket per client; one collector. Reconnect covers the socket; collector restart is 9.4. The mock has none outside the page.

### Security architecture

1.6 adds a client only; the server (4.4) is loopback-only. The trust edge is every inbound frame: `parseServerMessage` then `parseEvent`. Details in Section 3.


### Async ordering

Invariant (I1): the state a subscriber holds equals `reduce(latest snapshot of the current epoch, every later delta with seq > cursor, in seq order)`, and each event id is applied at most once while it stays in the ring. Boundary: from `subscribe` until `unsubscribe`, across any number of sockets.

```
  op A: old socket          op B: reconnect timer / new socket        shared state
  ------------------------- ----------------------------------------- -------------------------
  close event                                                          status=reconnecting
                            timer fires, new WebSocket, hello(e2)      current = socketB
  late onmessage(event)                                                ?? applies to e2 state
                            snapshot(e2, seq=K)                        state replaced
```

- Order 1 (late old-socket frame after new hello): without a guard it applies an epoch-1 delta onto epoch-2 state. **Mechanism required (S4-3): every handler checks `socket === current`, else ignore.** With it, both orders give I1.
- Order 2 (unsubscribe during backoff wait, then timer fires): timer cleared on unsubscribe; handler also checks `status !== 'closed'`. Both orders give no socket.
- Order 3 (setClock backward while a playback tick is queued): both run on the main thread with no `await` between read and apply; the tick reads the clock when it runs, so it delivers from the rebuilt position. Mechanism: synchronous apply path (no `await` between parse, apply and callbacks) — an implementation rule, tested by S4-3's test harness with a fake timer.
- Order 4 (emit during seek): `emit` and `setClock` are synchronous; either order gives I1 (an emitted event before a backward seek is lost by the rebuild — the rebuild replays the mock stream only). **S4-4 WARNING:** a backward seek discards emitted events. Stated in the contract; e2e must emit after seeking.

Regression proof: a fake WebSocket + fake timer test that holds the old socket's message, opens the new socket, then releases the old message (order 1), and an unsubscribe-then-fire test (order 2).
